# Freebyrd

A local-first context assistant for macOS, in Rust. Double-tap Option in any app; Freebyrd reads what is on screen and answers questions about it, and about the person's work, with Claude. It keeps a local memory of that work (Claude Code sessions, browser history and pages, email threads, Fireflies meetings), writes a recap of each day, puts promises the person makes in work conversations on Apple Calendar, and nudges about anything calendar-able it sees on screen; it also spots work the person repeats and suggests skills and scheduled jobs, running only the ones they approve. Cards wait in the notch, which glows and widens while they do. `README.md` has the full design, test results and history; read the relevant part before larger changes. `littlebird/FINDINGS.md` (one folder up) records how Littlebird, a similar product, does the same things; consult it when designing a feature, and cite it where a design follows it.

The source folder is still named `context-app`: renaming it would break the unpacked extension loaded in the user's Arc.

## Layout

- `crates/capture`: library. Accessibility reader (`ax`, `snapshot`, `text`), browser page store (`browser`), on-demand bridge client (`bridge`).
- `crates/ax-probe`: CLI that reads an app. The `tap-sim` binary sends synthetic Option taps (`--activate PID`, `--single`).
- `crates/browser-host`: Chrome native messaging host `com.freebyrd.browser_host`, with `install`, `uninstall` and `reload` subcommands.
- `crates/freebyrd`: the Tauri app (binary `freebyrd`). `tap.rs` double-tap detector and the ⌘⌥ shortcut (Command and Option pressed together on their own: the to-do list), `context.rs` screen capture (the window's text and the part of it in view), `picture.rs` the picture of the window that goes with a question, `claude.rs` the overlay's question (screen plus memory, and the thread's earlier turns for a follow-up), `models.rs` which model answers it, `worker.rs` background memory reader, recaps, promises, drafts, connectors and the daily suggestion step, `watcher.rs` reads the window in front for events to nudge about and for moments (what the person just started, weighed on a thread of its own), `whatsapp.rs` reads WhatsApp's open chat and chat list by their element identifiers, `claude_app.rs` the person's own messages in the Claude app's chat in front (by web class, for moments), `notch.rs` hangs the window from the notch and shows the glow, `live.rs` what the closed notch keeps in view beside it (to-dos due, a Run now job's progress, night shift, Claude Code sessions, what Claude Code read through the context connector; it also turns the connector's asks into consent cards), `sessions.rs` the person's Claude Code sessions in the desktop app and where each stands (the to-do list's Sessions tab, the closed notch and the iPad's board read it), with Push, `hover.rs` lets the closed island take a click only while the pointer is over it, `frame_rate.rs` turns off WebKit's 60 fps cap so the island animates at 120 Hz, `companion/` the iPad app's server (README "Freebyrd for iPad": `http` a small HTTP server, `pair` pairing and the Mac-only pairing page, `api` the iPad's calls, most of them the notch's own, `board` what only the iPad shows, `push` notifications, `state` its JSON files under `Application Support/Freebyrd/companion`), `companion-ui/` the iPad app's files, built into the binary, `ui/` plain HTML/CSS/JS with no build step: a black island that opens out of the notch like the Dynamic Island, with the to-do list behind the checklist icon at its top right (where the character count was).
- `crates/memory`: library and the `freebyrd-memory` CLI. `store` (SQLite schema and migrations; `open_read_only` for readers that must never migrate or write), `ingest` (Claude Code, browser history, saved pages and their email threads), `digest` (a day per project), `recap`, `cards` (with buttons and data), `recall` (memory for a question), `conversations` (chats, threads, meetings and their messages), `plans` (promises and nudges; card buttons; the notch's Up next line), `promises`, `quick` (the notch's quick asks, picked from the app in front and the memory), `day` (Plan my day: the day as blocks to add, inside the person's usual hours), `screen` (event-like lines on screen), `connectors` (Fireflies, Notion), `transcripts` (what was said in a meeting, read when a question asks), `routines` (repeated work: `detect` finds it with plain code, `suggest` drafts a fix with Claude as a Yes/No card, `jobs` writes approved skills and runs approved scheduled jobs through `launchd`, `skills` lists the skills the person already has), `calendar` (client for Freebyrd Calendar), `agenda` (the agenda written into a work event's calendar notes), `drafts` (step 5: from the working day before a promise or Notion task is due, a Draft card with what is missing and the deliverable or an update to send), `moments` (ideas at the moment they help, in any app: a page or window by its title, the person's last message in an AI chat or to Claude Code; pages read, earlier sessions and chats, and skills, ranked by Jev and picked by Sonnet into an Idea card with something to paste right there; see README "Ideas at the moment"), `jev` (TypeSafe's Jev over curl: ranks the ideas for a moment, and runs the shadows on trial; see README "Jev"), `todos` (the to-do list behind the notch's checklist icon: promises, Notion tasks, undated meeting action items and typed ones; Waiting on, with Notion tasks owed to the person and threads waited on; Done; see README "To-do list and people"), `asks` (work threads where the person waits on the other side, read with Haiku when they get a new message, for Waiting on), `progress` (the list follows the work: a Claude Code session gone quiet, or a reply in a thread tied to an item, read with Haiku, moves items, closes them or hands them back; see README "Following the work"), `people` (one page per person, joined by plain code from WhatsApp chats, Gmail senders and their addresses, Fireflies attendees and owners), `night` (night shift: work queued before the person stops, run while they are away; `blender` previews every 4th frame and finals of approved previews, `list` works a list of tasks on a worktree branch started from the person's uncommitted work, or on a copy of a project without git, with the project's check after each (tsc or `cargo check`), and Keep applies it uncommitted, `media` reels, thumbnails, contact sheets and blank-frame checks with ffmpeg, `sandbox` macOS's sandbox for scripts, `run` the start check, runner and morning card, `suggest` tonight's picks from what is owed and recent work, `stop` the easy stop: near the usual stop, one tap queues tonight's picks, favouring what is open; see README "Night shift"), `brief` (the context connector's full brief, kept as a preview: a folder's project, what is due, the latest recap's open items, the matching meeting's action items, stalled or uncommitted sessions, the latest sessions there and people by name, each line dated, sourced and marked seen, guessed or confirmed, at most 1,500 characters, as of a time; plain code), `threads` (the same items grouped into live threads: the index a session gets at its start, about 400 characters, and one thread's details on request), `connector` (what Claude Code may read: consent per tool and project, pending asks as `access` cards, receipts with no text, the daily cap, the hook's and MCP tools' answers, the notch line and Who read what, the two weeks' report; its records are `connector.db`; the `freebyrd-connector` binary is its hook and stdio MCP server; see README "Context connector"), `redact`, `exclusions` (mirrors `extension/exclusions.js`), `time` (working days run 04:00 to 04:00).
- `crates/claude-cli`: every Claude call goes through it (`stream` for the overlay, `ask` for recaps and extraction, `fetch` for connector reads, `run_job` for a scheduled job the person approved, `agent` for a night shift job, the one call that may change files), plus `data_element` for wrapping untrusted text and `connected_servers` (the MCP servers connected now). `find_cli` picks the newest Claude Code on the Mac (now the desktop app's bundled 2.1.288; the one on PATH is 2.1.107).
- `crates/calendar`: `freebyrd-calendar`, built into `Freebyrd Calendar.app` (`install`), which adds and removes events in the "Freebyrd" calendar through EventKit. Started with `open` so macOS gives it calendar access by its own name.
- `extension/`: Manifest V3 extension, ID `aoleafdlidoeidiadgoofcojpnenlpff` (fixed by the `key` in manifest.json; the private key is in `~/Library/Application Support/Freebyrd/extension-key.pem`).
- `fixtures/`: test documents and pages. `extract-test.html`, `gmail-test.html` and `chat-test.html` check `extension/content.js` (serve the project root over http, open the page; its title becomes PASS or FAIL).

## Invariants

- The extension owns the rules for web pages. If it declines (paused, excluded site) or does not answer, Freebyrd reads nothing for that browser. Never fall back to Accessibility for the same page.
- The extension cannot see an incognito window it is not allowed in, or another profile's window; asked for "the last focused window", it answers with another window's page. So a read carries when the browser was seen in front (`Target::seen_at_ms`, `frontAtMs`), the extension reads the window that had focus then from its focus log and declines with `hidden-window` if that was one it cannot see, and `context.rs` also drops a page whose title is unrelated to the front window's (`browser::window_shows`, loose because Arc shortens tab names). Either way nothing is read and nothing is pictured. Changing the read request means installing a new `browser-host` and reloading the extension.
- Password managers and System Settings are never read (`EXCLUDED_APPS` in `context.rs`).
- Screen text, memory and recaps are untrusted. Insert them into the UI as text, never HTML; the Markdown renderer in `ui/app.js` builds elements and sets their text. Send them to Claude inside `<screen>`, `<in_view>`, `<memory>` or `<activity>` built with `claude_cli::data_element`, marked as data, over stdin.
- A question's picture of the window (`picture.rs`) is taken only when that window's text could be read: never an excluded app, a page the extension declined, or an incognito window. It stays in memory, is never written to disk or the memory database, and cannot be redacted, so nothing but the overlay's question sends it.
- Quick asks and Up next never put screen or memory text (a chat's name, a plan's title) in the question they send; the screen and the plan go only inside `<screen>` and `<memory>`. Their labels may show it, as text.
- Claude runs through the `claude` CLI with the user's login, only via `crates/claude-cli`: `--tools "" --strict-mcp-config --disallowedTools "mcp__*" --setting-sources "" --disable-slash-commands --no-session-persistence`, Haiku 5.5, except notch questions that ask for things to be put together (meetings, recaps, drafts, decisions, whether something on screen fits their projects), which `models.rs` sends to Sonnet 5.5 (the user asked for a model picker by task, 2026-10-13). The overlay never names the model that answered (the user's rule); only the log does. Keep these calls tool-less, with one exception: the overlay's question (`claude.rs`, `stream` with `Tools::WebSearch`) may search the web (the user asked for it, 2026-10-13). Web search only: `WebFetch` stays denied, since opening a page lets screen or memory text send private details to an address of its choosing; opening pages would need a step that never sees screen or memory. Each query shows in the overlay as a note. Without `--no-session-persistence`, Freebyrd's calls would land in `~/.claude/projects` and be read back as the user's activity.
- `claude_cli::fetch` (with `run_job`, a fetch for a scheduled job the person approved: its approved prompt, its own folder, a $0.50 budget) is the only call with connector tools, and `agent` (night shift, below) the only one with file and shell tools: a fixed prompt Freebyrd writes (never screen, message or page text, nor the person's question), only named reading tools of the needed connector, its writing tools denied by name, every other server denied, `dontAsk`. Its answer is untrusted data. A question about meetings runs the Fireflies read first (`connectors::before_question`); only dates and Fireflies meeting IDs reach those prompts. A transcript read stores the tool's own output (`fetch_with_results`), never the model's retyping.
- All AI processing uses that CLI (the user's decision); no local models. One exception, also the user's decision (2026-10-13): `memory::jev` asks TypeSafe's Jev (typed judgments; it writes nothing) over HTTPS, for six shadows (README "Jev") that log to `jev/<use>.jsonl` and change nothing the person sees; a shadow goes live only after the person has read its report. One use is live by the person's decision (2026-10-13): ranking ideas for a moment (`moments`), with no shadow first. Choosing memory for notch questions is not approved. Each shadow sends only what the README lists; the key stays in the Keychain (`freebyrd-typesafe`) and reaches curl on stdin, never in arguments, files or the memory; without a key nothing is sent, and tests never read it. A shadow never stops the step it watches: its errors are log lines. Every Jev request goes through `jev::ask` with its use's name, which counts it and refuses it past the day's 10 million tokens or a shadow's share (2 million each, 4 million together), so shadows never starve the live use (README "Jev's budget"); raising any of these is the person's decision.
- The memory database stays in `~/Library/Application Support/Freebyrd/`, never under Documents (iCloud). Run text through `memory::redact` before storing it and before sending it.
- Only what is listed under "What leaves the Mac" in the README goes to Claude. Update that list when that changes. The screen watcher never sends a whole screen, only event-like lines with a little context (`memory::screen::candidates`), and only from the person's own places (`memory::screen::is_own_place`: their mail, chats and workspaces, a tool's `app.` subdomain, app windows other than reading apps). A date on a product's site or in an article is someone else's; never widen this to "any site they visit often" (the person's ask, 2026-10-13; README "Watching the screen").
- Promises go on the calendar by themselves only from work conversations (email threads, Fireflies meetings, chats marked work); everything seen on screen is a nudge that waits for the person's press, and so is an event a notch answer offers (a ` ```event ` block, `plans::add_offered`; README "Events in answers"): the answer never adds anything itself. Freebyrd only adds to and removes from its own "Freebyrd" calendar (`freebyrd-calendar remove` refuses other events).
- The glow never takes the keyboard: show the closed overlay only through `notch::show_inactive`. Only opening the overlay may focus it (a double tap, ⌘⌥, the menu, or a click on the closed island). The closed window lets clicks through to the menu bar except while the pointer is over the island's own shape (`hover.rs`, which reads the pointer's position only, never clicks or keys); set that only on the main thread, re-checking that the overlay is not open, so the open notch never ignores clicks.
- Step 6 sets up nothing without the person's Yes on its card. Detectors are plain code; Claude drafts from minimal evidence only (counts, dates, titles, project and folder names, the first 100 characters of prompts, redacted), never page or chat text. A job's prompt is the approved text, never screen, message or page text; jobs read with their connectors' reading tools only, and their output is untrusted data. Freebyrd's runs must never be read back as the person's activity: they run from folders under `Application Support/Freebyrd` (Claude Code ingestion skips folders named with "Application-Support-Freebyrd") with `--no-session-persistence`. While developing, use only `suggest --test` suggestions and remove them with `suggest --clean-test`.
- Plan my day (`day`) plans a day worth living, not work stacked into every hour (the user's rule, 2026-10-13): at most 6 hours of planned work, ending two hours before the person's usual stop, and meals, breaks, movement and non-work time every day. Its blocks are plans of kind `block:*` and cards of kind `block`, which never glow or join the opening card list.
- Step 5 drafts only (the user's ask, 2026-10-13): a draft waits on its card and is never sent; Copy is the only way out. - The keyboard tap never records which key was pressed, only which modifiers are down; debug logging covers Option and the ⌘⌥ shortcut only. The shortcut counts only when Command and Option go down and are let go within 0.8 s with no other modifier, key or click in between (so ⌘⌥Esc, ⌘⌥D and ⌘⌥-drags never open it).
- Ideas at the moment (`moments`, the person's decisions of 2026-10-13): a moment may use only the window's title, the site or app, the person's own last three messages in an AI chat and their first there (`extension/content.js` `chatAsk`, newest first, then the count and the first; in the Claude app, `claude_app` reads the chat in front by the `user-message` web class) and their last request to Claude Code; never the assistant's replies, other people's messages or page text. A chat or Claude Code session is weighed at its start and again only when Jev, asked one short question, finds a later message turned to new work (the person's idea, 2026-10-13, for budget's sake). The last message travels only on reads the desktop side asks for and never reaches the page store (`PageStore::record` drops it, like `in_view`). Ideas come from pages read, earlier Claude Code sessions and AI chats, and installed skills (X bookmarks were a source until 2026-10-16); Jev ranks them all and Claude sees only a shortlist (README "Ideas at the moment" lists what leaves the Mac).
